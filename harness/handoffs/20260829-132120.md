## What I was mid-thought on

The exclude list is not clean and I filed ccp-4kq.5 for it. I got to green by
iterating `swift build` and excluding whatever failed, four waves of it. Only the
first wave (24 files) actually names a UI type. The other 14 fell out behind an
already-excluded file, so some of them would compile fine if their blocker came
back. I didn't unpick it because green mattered more at that point, but it means
the list currently overstates how bad the boundary is.

The thing that still nags: replacing upstream's executableTarget rather than
sitting beside it felt like the only option (SwiftPM won't share sources, and an
executable can't be imported), but it does mean their app is unbuildable from
this fork forever. That's fine for us and it's what the BRIEF wanted. It's also
the sort of decision that's very cheap now and very expensive to revisit once
there's real code on top, so if it's wrong, it's wrong now.

Rejected and still slightly tempting: a `sources:` include-list instead of
`exclude:`. It would state intent better — "these are the engines we build" —
and wouldn't need the cascade entries at all. I backed off because naming
individual UI leaf files to pull back in (PermissionGuideOverlay and friends)
risked dragging Theme.swift and SharedUI.swift and half of UI/ behind them, and
I couldn't cheaply bound it. Worth revisiting alongside ccp-4kq.5.

## Watch out for

- `Permissions.showGuide` is `@MainActor` on purpose. Both reviewers landed on
  it; the tempting comment ("safe, only called from the main thread") would have
  been false — Permissions is a plain ObservableObject and that same file hops
  to DispatchQueue.global in three places. Don't relax it back.
- Upstream's .gitignore ignores AGENTS.md, CLAUDE.md, and *.xcodeproj. We track
  all three. Every merge will try to bring those lines back; the reasons are
  written in .gitignore itself.
- `origin` is the user's fork, `upstream` is vorssaint-utils. Per BRIEF, ask
  before merging upstream.
