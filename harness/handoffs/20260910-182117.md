# handoff 2026-09-10

Rebuilt Craft sync on a recorded base (ccp-c2x5, closed) — the conflicted-copy
bug was a diff spanning two markdown dialects, not a race. User live-tested a
few simple cases and it holds; they are still trying it, so treat the fix as
promising rather than proven.

What I was mid-thought on, and what a diff will not tell you:

- **`base.isAligned` is load-bearing and I do not know how often it is false in
  the wild.** The push names Craft ids by position, which only means anything
  while our slices and Craft's blocks stand one-to-one. When they do not,
  `BlockPushPlan.rewrite` deletes and reposts that pad's writable blocks. That
  is correct but loud, and it breaks Craft block links. Craft splits blocks we
  keep whole (a soft-wrapped line), so misalignment is *normal*, not
  exceptional — I could not tell from here whether a real pad sits misaligned
  often enough for the repost to be a visible problem. If sync looks churny in
  live use, measure that first. ccp-7li7 (emit Craft's spelling) would reduce
  it but does not address splitting, which is the structural half.

- **The half-applied-round hole I decided to live with.** If a DELETE fails,
  Craft keeps a block the pad dropped. The failed round records Craft's text as
  both sides of the base, so the pad reads as leading and the retry removes it —
  that path is tested. But if the pad is *also* misaligned at that moment,
  `plan`'s `old == slices` shortcut returns empty and the orphan stands until
  the user next edits that region. I chose the shortcut over reconciling on
  every misalignment because reconciling would churn constantly, which is the
  failure mode this whole bead was about. Still feels like the weakest seam.

- **`stashIDs` is now write-nothing legacy** and I left the reader in place so
  old Conflicted-copy sections stay out of the pad. It empties only as the user
  deletes them in Craft. ccp-d9v6 would offer a cleanup; until then a user with
  a polluted document carries the exclusion list forever.

Next I would pick up ccp-a77s — the "Error on first open" half is untouched and
unexplained, and now that the sync is quiet it should be much easier to see.

The durable lesson is in `bd recall the-push-plan-is-not-a-cleanliness-oracle`;
the corollary matters as much as the bug — 883 tests were quiet because every
fake echoed back exactly what was sent. `NormalisingCraftTransport` is the fake
that does not, and new sync tests belong against it.
