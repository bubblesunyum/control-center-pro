The scratchpad's markdown adoption is DONE and closed (ccp-dn5) — pad at 300pt,
block model and preview path deleted, gate green. The Craft API is no longer
guesswork: a live round trip settled byte-stability, and the answer reshaped the

What I was mid-thought on: whether tier 2 of ccp-prk — registering the 15
per-colour <highlight> tags as static delimiter pairs — is clever or grotesque.
It works, the seam takes it, and it is ~20 lines. But fifteen near-identical
extension instances to express one construct is the shape of a thing that should
have been one parameterised rule, and building it might make the upstream tag-
syntax ask (ccp-jqj) look already-solved when it is only worked around. I left
it unfiled deliberately. If it gets built, build it AFTER upstream answers.

Rejected and still tempting: writing the markdown/Craft splitter now with Apple's
swift-markdown, rather than waiting on ccp-jqj. Everything is designed, the
parser is one dependency away, and it would move ccp-2zi.5 and .6 today. I kept
saying no because MarkdownEngine already computes exactly the ranges we need —
including the GFM checkbox and indent depth — and shipping a second parser to
avoid one conversation with a maintainer trades a permanent hazard (two parsers
disagreeing about block boundaries, so the pad lies about what it will push) for
a few days of waiting. If upstream declines, the fallback is written up on
ccp-jqj and it is a small change.

(trap: review-sh-ships-stale-captures, now joined by

not have an explanation for. Something about how the packet hands captures to
